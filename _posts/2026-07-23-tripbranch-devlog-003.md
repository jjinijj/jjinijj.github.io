## 오늘의 개발 주제

TripBranch에서 장소를 추천하려면 장소명, 위치, 운영시간 등 장소의 상세 정보가 필요하다.

처음에는 추천 시점에 외부 API를 호출해 필요한 정보를 가져오는 방식을 고려했다. 하지만 API 구조를 확인한 결과, 장소 하나의 정보를 조회하기 위해 여러 번의 통신이 필요했고 추천 후보가 많아질수록 응답 시간이 크게 증가하는 문제가 있었다.

이번 작업에서는 기존 API 조회 흐름의 문제를 분석하고, 변경 빈도가 낮은 장소 정보를 DB에 미리 구축하는 방향을 정리했다.

---

## 기존 장소 정보 조회 흐름

현재 사용하는 API에서는 장소명만으로 장소 상세 정보를 직접 조회할 수 없다.

장소 상세 정보를 가져오려면 먼저 해당 장소의 고유 코드를 알아야 한다. 이 코드는 특정 좌표를 기준으로 일정 거리 안의 장소 목록을 조회했을 때 확인할 수 있다.

기본적인 조회 흐름은 다음과 같다.

```text
기준 좌표 설정
→ 주변 장소 목록 API 호출
→ 장소 목록에서 장소 코드 확인
→ 장소 코드로 상세 정보 API 호출
```

여기에 장소 상세 정보도 하나의 API에 모두 포함되어 있지 않고, 정보의 성격에 따라 두 개의 상세 API로 나뉘어 있다.

```text
주변 장소 목록 조회
→ 장소 코드 확인
→ 장소 기본 상세 정보 조회
→ 장소 소개·운영 정보 조회
```

따라서 하나의 장소에 필요한 정보를 모두 확인하려면 최대 3단계의 API 조회가 필요하다.

---

## 추천 후보가 많아질 때의 문제

추천할 장소 10개의 상세 정보를 가져온다고 가정하면 API 호출 구조는 다음과 같다.

```text
주변 장소 목록 조회: 1회
장소별 기본 상세 정보 조회: 10회
장소별 추가 상세 정보 조회: 10회
```

총 호출 횟수는 다음과 같다.

```text
1 + 10 + 10 = 21회
```

실제 테스트에서도 10개 장소의 정보를 조회하는 데 약 10초가 소요되었다.

추천 결과를 생성하기 전에 장소 정보를 가져오는 데만 10초가 걸리면, 이후 가중치 계산과 LLM 응답 생성 시간까지 더해져 사용자가 체감하는 대기 시간이 더 길어진다.

또한 추천 조건이 변경될 때마다 같은 장소의 정적인 정보를 반복해서 요청할 가능성도 있다.

---

## 기존 방식의 한계

외부 API에서 모든 정보를 실시간으로 조회하는 방식에는 다음과 같은 문제가 있었다.

- 추천 후보 수만큼 API 호출 횟수가 증가함
- 동일한 장소 정보를 반복해서 조회할 수 있음
- API 응답 속도에 전체 추천 시간이 영향을 받음
- 호출 제한이나 일시적인 API 오류에 취약함
- 여러 API에서 받은 데이터를 매번 결합해야 함
- 추천 로직을 테스트할 때마다 외부 API 상태에 영향을 받음

특히 장소명, 주소, 좌표, 카테고리와 같은 정보는 자주 변경되지 않는다. 이러한 데이터까지 추천 요청마다 다시 조회하는 것은 비효율적이라고 판단했다.

---

## 정적 장소 데이터 DB 구축 결정

API 호출 횟수와 추천 응답 시간을 줄이기 위해, 변경 빈도가 낮은 장소 정보는 DB에 미리 구축하기로 했다.

추천 요청이 들어오면 외부 API에서 모든 장소 정보를 새로 가져오는 대신, DB에서 후보 장소를 먼저 조회하고 필요한 실시간 정보만 외부 API로 보완하는 구조다.

```text
기존 구조

사용자 요청
→ 장소 목록 API
→ 장소별 상세 API
→ 장소별 추가 상세 API
→ 추천 계산
```

```text
변경 구조

사용자 요청
→ DB에서 장소 후보 조회
→ 필요한 실시간 데이터만 API 조회
→ 추천 계산
```

이 구조를 적용하면 장소 후보가 많아져도 장소별 상세 API를 반복해서 호출하지 않아도 된다.

## DB에 저장할 데이터 기준

모든 데이터를 DB에 저장하는 것이 아니라, 데이터의 변경 빈도를 기준으로 정적 데이터와 동적 데이터를 구분하기로 했다.

### 정적 데이터 후보

현재 DB 저장 대상으로 검토 중인 정보는 다음과 같다.

- 장소 코드
- 장소명
- 주소
- 위도와 경도
- 장소 카테고리
- 장소 설명
- 대표 이미지
- 이용 안내
- 운영시간
- 휴무일
- 문의처
- 주차 정보
- 반려동물 동반 가능 여부
- 장애인 편의시설 정보

운영시간과 휴무일은 변경될 가능성이 있지만, 날씨나 혼잡도처럼 짧은 주기로 바뀌는 데이터는 아니다. 따라서 MVP에서는 DB에 저장하되, 데이터 출처와 마지막 갱신 시점을 함께 관리하는 방식을 검토하고 있다.

### 동적 데이터 후보

추천 요청 시점에 조회해야 할 가능성이 높은 정보는 다음과 같다.

- 현재 날씨
- 시간대별 날씨 예보
- 실시간 혼잡도
- 현재 위치
- 이동 거리와 예상 이동 시간
- 임시 휴무 또는 실시간 운영 상태

동적 데이터는 사용자의 요청 시점과 위치에 따라 달라지므로 외부 API 조회가 필요하다.

---

## 변경된 데이터 조회 구조

장소 추천에 필요한 데이터를 다음과 같이 구분한다.

| 구분 | 데이터 예시 | 조회 방식 |
|---|---|---|
| 정적 장소 정보 | 장소명, 주소, 좌표, 카테고리 | 내부 DB |
| 준정적 운영 정보 | 운영시간, 휴무일, 이용 안내 | 내부 DB 및 주기적 갱신 |
| 실시간 상황 정보 | 날씨, 혼잡도, 현재 운영 상태 | 외부 API |
| 사용자 정보 | 현재 위치, 선호 조건, 거절 이력 | 현재 세션 |
| 추천 결과 | 점수, 순위, 추천 이유 | 추천 시점에 계산 |

이 구조를 통해 추천 요청마다 반드시 필요한 API만 호출할 수 있다.

---

## 기대 효과

정적 장소 데이터를 DB에 구축하면 다음과 같은 효과를 기대할 수 있다.

### API 호출 감소

장소별 상세 정보를 실시간으로 호출하지 않아도 되므로, 후보 장소 수에 비례해 증가하던 API 호출을 줄일 수 있다.

### 추천 응답 시간 단축

장소 기본 정보는 DB에서 빠르게 조회하고, 날씨와 혼잡도처럼 필요한 정보만 외부 API에서 가져올 수 있다.

### 추천 로직 테스트 안정화

외부 API 상태와 관계없이 동일한 장소 데이터를 사용해 가중치 계산과 프롬프트 테스트를 반복할 수 있다.

### 데이터 구조 통일

서로 다른 API에서 제공되는 장소 정보를 내부 스키마로 통합해 추천 로직에서 일관된 형식으로 사용할 수 있다.

## 함께 고려해야 할 문제

DB를 구축한다고 해서 모든 문제가 해결되는 것은 아니다.

운영시간이나 휴무일처럼 변경될 수 있는 정보를 저장하면 오래된 데이터가 추천에 사용될 위험이 있다. 따라서 각 데이터의 갱신 주기와 마지막 갱신 시점을 함께 관리해야 한다.

또한 외부 API의 장소 코드가 변경되거나 장소가 폐업하는 경우를 어떻게 반영할지도 검토해야 한다.

현재는 다음 기준을 추가로 확인하고 있다.

- 어떤 항목을 정적 데이터로 분류할 것인지
- 운영 정보를 얼마나 자주 갱신할 것인지
- 폐업하거나 변경된 장소를 어떻게 확인할 것인지
- API 데이터와 DB 데이터가 다를 때 무엇을 우선할 것인지
- 추천 시점에 반드시 다시 조회해야 할 정보가 무엇인지

## 정리

장소 상세 정보는 장소명으로 직접 조회할 수 없고, 주변 장소 목록에서 장소 코드를 얻은 뒤 여러 상세 API를 호출해야 한다.

장소 10개의 전체 정보를 확인하려면 최대 21회의 API 통신이 필요했고, 약 10초의 응답 시간이 소요되었다.

이 문제를 해결하기 위해 장소명, 주소, 좌표, 운영 정보 등 변경 빈도가 낮은 데이터는 DB에 미리 구축하고, 날씨와 혼잡도처럼 실시간성이 필요한 데이터만 외부 API에서 조회하는 구조로 변경하기로 했다.

> 정적 데이터는 미리 구축하고, 추천 시점에는 변하는 정보만 조회한다.
