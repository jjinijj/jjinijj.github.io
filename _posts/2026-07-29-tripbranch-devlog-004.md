## 작업을 시작한 이유

TripBranch에서는 장소 추천 시 TourAPI의 관광지 정보와 별도의 집중률 데이터를 함께 사용한다.

그런데 두 데이터의 장소 수가 일치하지 않았고, 집중률 API에는 TourAPI의 `content_id`, 주소, 좌표가 제공되지 않았다.

집중률 API가 제공하는 장소 식별 정보는 다음과 같았다.

* `areaCd`
* `signguCd`
* `tAtsNm`
* `baseYmd`
* `cnctrRate`

따라서 집중률 데이터의 관광지명인 `tAtsNm`만으로는 TourAPI의 어떤 장소와 연결되는지 안정적으로 판단하기 어려웠다.

이 문제를 해결하기 위해 먼저 TourAPI 장소 데이터를 최신 상태로 정리하고, 집중률 장소명과 TourAPI의 `content_id`를 연결하는 별도의 매핑 테이블을 구축하기로 했다.

```text
TourAPI 장소 데이터 최신화
→ 누락 및 중복 장소 검증
→ 집중률 장소명과 TourAPI 장소 비교
→ 자동·수동 매핑
→ 매핑 테이블 구축
→ Supabase 반영
```

## 1. TourAPI 장소 최신 스냅샷 생성

종로구 조건으로 TourAPI 장소 목록을 다시 수집해 기존 DB와 비교했다.

| 구분                | 장소 수 |
| ----------------- | ---: |
| 기존 DB 장소          | 882개 |
| 최신 TourAPI 목록     | 847개 |
| 신규 장소             |   0개 |
| 최신 목록에서 누락된 기존 장소 |  35개 |

최신 목록에는 새로운 장소가 없었지만, 기존 DB에 저장된 장소 중 35개가 더 이상 목록에서 조회되지 않았다.

다만 외부 API에서 한 번 누락됐다는 이유만으로 해당 장소를 즉시 삭제하거나 비활성화하면 일시적인 응답 누락을 실제 데이터 삭제로 잘못 판단할 수 있다.

따라서 동일 조건으로 총 3차 검증을 진행하기로 했다.

---

## 2. 누락 장소 35개 재검증

누락된 35개의 `content_id`를 대상으로 다음 항목을 교차 확인했다.

* 종로구 지역 목록 재조회
* `detailCommon2` 공통 상세 조회
* `detailIntro2` 소개·운영 정보 조회
* 장소명 검색을 통한 대체 ID 확인

3차 검증 결과는 모두 동일했다.

| 검증 항목         |   결과 |
| ------------- | ---: |
| 매회 지역 목록      | 847개 |
| 매회 누락 장소      |  35개 |
| 오류 및 타임아웃     |   0개 |
| 검증 결과가 달라진 장소 |   0개 |

누락된 장소 중 33개는 두 상세 API에서도 모두 `no_data`로 확인됐다.

처음에는 다음 두 장소가 새로운 ID로 교체된 것으로 보였다.

* 일품당프리미엄
* 청하고려인삼

하지만 확인 결과, 새로운 ID가 발급된 것이 아니라 기존 DB에 같은 장소가 서로 다른 `content_id`로 중복 등록되어 있던 사례였다.

| 장소      |  누락된 ID | 유지되는 ID |
| ------- | ------: | ------: |
| 일품당프리미엄 | 2654165 | 2544584 |
| 청하고려인삼  | 2498434 | 2909934 |

최종적으로 누락 장소 35개를 다음과 같이 분류했다.

* 중복 정리로 사라진 ID: 2개
* 삭제 또는 비공개 전환 추정: 33개
* 실제 신규 ID로 교체된 장소: 0개

## 3. 기존 장소 정보 변경 검토

기존 DB와 최신 TourAPI 데이터를 기계적으로 비교했을 때는 총 137개 장소에서 변경이 감지됐다.

그러나 이 중 130개는 좌표의 소수점 자릿수 차이처럼 실제 서비스 운영에 의미가 없는 변경이었다.

예를 들어 좌표값이 실제로 이동한 것이 아니라 API 응답의 소수점 표현 자릿수만 달라진 경우까지 모두 변경으로 판단되고 있었다.

따라서 기계적인 차이를 전부 반영하지 않고, 주소나 좌표처럼 실제 장소 정보에 영향을 주는 변경만 선별했다.

운영상 의미 있는 변경이 확인된 장소는 총 7개였다.

* 서울 동관왕묘
* 동십자각
* 서울 관상감 관천대
* 종로꽃시장
* 두레유
* 헤리티지클럽
* 우리소리도서관

주요 변경 내용은 다음과 같다.

* 누락된 주소 정보 보완
* 수 m 단위의 실제 좌표 조정
* TourAPI 수정 시각 갱신

> 데이터의 문자열이 다르다는 이유만으로 모두 변경하지 않고, 추천과 위치 판정에 영향을 주는 변경만 반영했다.

## 4. Supabase 장소 데이터 동기화

검증 결과를 기준으로 Supabase의 장소 데이터를 최신 상태로 동기화했다.

| 상태       | 장소 수 |
| -------- | ---: |
| 활성 장소    | 847개 |
| 비활성 장소   |  35개 |
| 전체 보존 장소 | 882개 |

누락된 장소는 물리적으로 삭제하지 않고 `is_active=false`로 변경했다.

비활성 사유는 `missing_from_source`로 기록했다.

최신 목록에 포함된 장소는 `content_id`를 기준으로 갱신하고, 목록에서 누락된 장소만 비활성화했다.

```text
최신 목록 포함
→ content_id 기준 upsert
→ 장소 정보 갱신

최신 목록 누락
→ is_active = false
→ inactive_reason = missing_from_source
```

장소를 삭제하지 않고 비활성화한 이유는 다음과 같다.

* 과거 추천 및 데이터 이력을 보존할 수 있음
* 잘못된 비활성화 판단 시 복구가 쉬움
* 장소가 다시 API에 등장할 경우 재활성화할 수 있음
* 기존 참조 관계가 깨지는 것을 방지할 수 있음

동기화 전 DB 상태는 별도의 CSV로 백업했다.

## 5. 집중률 장소와 TourAPI 장소 비교

TourAPI 장소 데이터를 최신화한 뒤 집중률 API의 장소명과 TourAPI 장소를 연결하는 작업을 진행했다.

집중률 API에는 장소 고유 ID나 좌표가 없기 때문에 `tAtsNm`을 TourAPI의 `content_id`에 매핑해야 했다.

초기 자동 매칭 기준은 다음과 같이 구성했다.

### 완전 일치

집중률 관광지명과 TourAPI 장소명이 완전히 같은 경우 자동으로 연결했다.

### 정규화 일치

공백, 괄호, 특수문자 등 표기 차이를 제거한 뒤 이름이 일치하면 자동으로 연결했다.

### 검토 필요

문자열 유사도는 높지만 동일 장소라고 확정하기 어려운 경우 `review_required`로 분류했다.

### 미매칭

적절한 후보가 없는 경우 `unmatched`로 분류했다.

```text
집중률 장소명
→ 완전 일치 확인
→ 표기 정규화 후 일치 확인
→ 유사도 후보 생성
→ 수동 검증
→ content_id 확정 또는 미매칭 유지
```

## 6. 모호한 장소 수동 검증

자동으로 확정하기 어려운 장소는 실제 장소 정보와 운영 정보를 개별적으로 확인했다.

주요 수동 매핑 결과는 다음과 같다.

| 집중률 장소명       | TourAPI 대표 장소 | content_id | 처리    |
| ------------- | ------------- | ---------: | ----- |
| 묘각사(서울)       | 낙산묘각사         |     128872 | 수동 매핑 |
| 익선동           | 익선동 한옥거리      |    2650046 | 수동 매핑 |
| 종로6가 대학천 책방거리 | 대학천 책방거리      |     132202 | 수동 매핑 |
| 경찰박물관         | 국립경찰박물관       |    2782735 | 수동 매핑 |
| 쌈지길           | 쌈지길           |     128553 | 수동 확인 |

익선동은 중복된 두 개의 TourAPI ID가 존재했으며, 상세 정보와 운영 정보가 더 완전한 ID를 최종 대표 장소로 선택했다.

`쉼박물관`과 `떡박물관`은 유사한 후보로 나타났지만 실제로는 서로 다른 장소로 확인되어 매핑하지 않았다.

유사도가 높다는 이유만으로 자동 연결하면 잘못된 장소의 집중률이 추천에 반영될 수 있으므로, 동일 장소임을 확인할 수 없는 관계는 `manual_rejected`로 기록하기로 했다.

## 7. 청와대 별칭 처리

집중률 API에는 `청와대`가 제공되지만, TourAPI에서는 이를 별도의 장소 행으로 연결하기보다 `청와대 앞길`의 별칭으로 처리하는 것이 적절하다고 판단했다.

최종 구조는 다음과 같다.

```text
대표 장소명: 청와대 앞길
content_id: 126533
집중률 별칭: 청와대
```

청와대를 별도의 매핑 행으로 만들지 않고 한 개의 `content_id`가 여러 집중률 장소명을 지원하도록 별칭 배열을 사용했다.

이 결정으로 인해 보조 검증 과정에서는 집중률 원본이 113개로 집계됐지만, 최종 CSV에서는 청와대를 별도 행으로 두지 않아 112개 항목이 되었다.

> 같은 실제 장소를 가리키는 여러 이름은 별도 장소로 중복 저장하지 않고 대표명과 별칭으로 통합한다.

## 9. 집중률 매핑 테이블 설계

집중률 장소명과 TourAPI 장소의 관계를 관리하기 위해 `place_concentration_mappings` 테이블을 생성했다.

주요 필드는 다음과 같다.

```text
place_concentration_mappings

- content_id
- primary_concentration_name
- concentration_aliases
- match_method
- confidence_score
- verified_at
- created_at
- updated_at
```

`content_id`는 `places.content_id`를 참조한다.

매핑 테이블에는 장소 좌표를 중복 저장하지 않았다. 좌표와 장소 기본 정보는 `places` 테이블을 기준으로 사용하고, 매핑 테이블은 집중률 장소명과 장소 ID의 관계만 관리한다.

향후 인근 장소를 대신 사용하는 proxy 검색이 필요할 경우에도 `places` 테이블의 좌표와 공간 인덱스를 활용할 예정이다.

## 10. Import 도구와 산출물 추가

매핑 데이터를 반복해서 검증하고 적재할 수 있도록 다음 도구와 문서를 추가했다.

* 집중률 매핑 migration
* CSV import CLI
* dry-run 기능
* import 테스트
* DB 설계 문서
* Supabase migration 문서
* 동기화 전 장소 백업 CSV
* 최종 변경계획 CSV

Import는 `content_id`를 기준으로 재실행 가능한 방식으로 구현했다.

같은 CSV를 다시 입력하더라도 중복 행이 생성되지 않으며, 비활성 장소는 import 대상에서 제외된다.

## 이번 작업의 주요 의사결정

### TourAPI를 장소 기준 데이터로 유지한다

집중률 API에는 장소 고유 ID와 좌표가 없으므로, 장소의 기준 식별자는 TourAPI의 `content_id`를 사용한다.

집중률 데이터는 독립적인 장소 데이터가 아니라 TourAPI 장소에 연결되는 부가 정보로 관리한다.

### 한 번의 누락만으로 장소를 비활성화하지 않는다

동일 조건의 목록 조회와 두 개의 상세 API를 총 3차례 검증해 결과가 동일한 경우에만 비활성화한다.

API의 일시적인 누락을 실제 장소 삭제로 잘못 판단하지 않기 위한 기준이다.

### 누락 장소는 삭제하지 않고 비활성화한다

현재 목록에서 사라진 장소는 추천 대상에서는 제외하지만, 데이터 이력과 참조 관계를 유지하기 위해 물리적으로 삭제하지 않는다.

### 기계적으로 감지된 변경을 모두 반영하지 않는다

좌표 소수점 자릿수처럼 서비스에 영향을 주지 않는 변경은 제외한다.

실제 주소, 좌표, 수정 시각 등 운영상 의미 있는 변경만 DB에 반영한다.

### 집중률 장소명 자체를 고유 식별자로 사용하지 않는다

동일한 장소가 여러 이름으로 제공되거나 이름이 변경될 수 있으므로, 장소명은 `content_id`에 연결되는 매핑 값으로만 사용한다.

### 자동 매칭과 수동 매칭을 구분한다

완전 일치와 정규화 일치는 자동 확정할 수 있지만, 문자열 유사도만 높은 경우에는 실제 동일 장소인지 확인한 뒤 수동으로 결정한다.

잘못된 후보는 `manual_rejected`로 남겨 같은 오매칭이 반복되지 않도록 한다.

### 매칭된 장소만 DB에 저장한다

확신할 수 없는 12개 장소는 잘못된 집중률 조회를 방지하기 위해 DB에 적재하지 않는다.

미매칭 데이터는 검증 CSV에 유지해 이후 데이터 보완 시 다시 확인할 수 있도록 한다.

### 동일 장소의 여러 이름은 별칭으로 관리한다

청와대와 청와대 앞길처럼 동일한 실제 장소를 가리키는 이름은 별도 장소 행으로 만들지 않는다.

대표 장소와 별칭 배열을 사용해 한 개의 `content_id`가 여러 집중률 장소명을 지원하도록 한다.

### 매핑 테이블에 장소 정보를 중복 저장하지 않는다

좌표와 기본 장소 정보는 `places` 테이블을 기준으로 사용한다.

매핑 테이블은 `content_id`와 집중률 장소명의 관계만 관리해 데이터 중복과 불일치를 줄인다.

### 동기화 전 데이터는 백업으로 보존한다

비활성화 기준이나 매핑 판단에 오류가 확인될 경우 이전 상태를 복원할 수 있도록 원본 데이터를 CSV로 보관한다.

### 갱신 작업은 재실행 가능하게 만든다

장소 동기화와 집중률 매핑 import는 `content_id` 기준의 upsert 방식으로 구성한다.

동일한 작업을 반복 실행하더라도 중복 데이터가 생성되지 않도록 한다.

## 변경된 데이터 구조

이번 작업을 통해 장소와 집중률 데이터의 관계는 다음과 같이 정리됐다.

```text
places
- TourAPI 장소 기준 데이터
- content_id
- 장소명
- 주소
- 좌표
- 운영 정보
- 활성 상태

place_concentration_mappings
- places.content_id 참조
- 집중률 대표 장소명
- 집중률 별칭
- 매칭 방법
- 신뢰도
- 검증 시각

집중률 원본 데이터
- tAtsNm
- baseYmd
- cnctrRate
```

추천 시에는 집중률 API의 `tAtsNm`을 매핑 테이블에서 조회해 TourAPI의 `content_id`를 찾고, 해당 장소의 기본 정보는 `places` 테이블에서 가져올 수 있다.

## 이번 작업에서 얻은 것

이번 작업은 단순히 장소 수를 맞추는 작업이 아니었다.

먼저 TourAPI 장소 데이터가 실제로 최신 상태인지 확인하고, 누락과 중복을 정리한 뒤에야 집중률 데이터를 안정적으로 연결할 수 있었다.

또한 장소명은 사람이 보기에는 같아 보여도 실제로는 다른 장소일 수 있고, 반대로 서로 다른 이름이 동일한 장소를 가리킬 수도 있다는 점을 확인했다.

따라서 장소명 문자열만으로 데이터를 자동 연결하기보다 기준 ID, 메타데이터, 수동 검증 결과를 함께 관리해야 한다.

> 데이터 매핑에서는 많이 연결하는 것보다 잘못 연결하지 않는 것이 더 중요하다.

## 정리

집중률 데이터와 TourAPI 장소 목록의 수가 일치하지 않아 두 데이터 간의 안정적인 연결 구조가 필요했다.

이를 위해 TourAPI 장소 목록을 다시 수집하고, 누락된 35개 장소를 목록·상세·검색 API로 3차 검증했다. 검증 결과에 따라 장소 847개를 활성 상태로 유지하고 35개는 이력을 보존한 채 비활성화했다.

이후 집중률 장소명을 TourAPI의 `content_id`에 연결해 112개 항목 중 100개를 매핑했으며, 별칭을 포함해 101개의 장소명을 지원할 수 있게 됐다.

또한 `place_concentration_mappings` 테이블과 재실행 가능한 import 도구를 추가해 장소 데이터와 집중률 데이터를 분리하면서도 안정적으로 연결할 수 있는 구조를 구축했다.

> TourAPI의 `content_id`를 장소의 기준 식별자로 사용하고, 집중률 장소명은 검증된 매핑과 별칭을 통해 연결한다.
