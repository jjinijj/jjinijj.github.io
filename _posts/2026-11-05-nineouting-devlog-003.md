## 오늘의 개발 주제

[#002](/nineouting/2026/11/01/nineouting-devlog-002.html)까지는 음성 인식 자체의 정확도를 올렸다. 그래도 틀린 글자는 남는다. 19분짜리 실제 회의 녹음을 음성 인식, 요약, 회의록 초안까지 끝까지 돌려 보니 "Terraform"이 "테로폰"으로 적힌 채 회의록까지 들어갔다.

회의록은 저장되고 검색 대상이 된다. 그래서 회의록 초안을 만들기 전에 오인식을 한 번 더 바로잡는 단계를 넣기로 했다.

처음 세운 규칙은 안전했지만 거의 아무것도 고치지 못했다. 오늘은 규칙을 어떻게 풀어 갔는지, 그리고 왜 풀어도 된다고 판단했는지 정리한다.

---

## 처음 설계

흐름은 이렇게 잡았다.

```text
회의 끝 요약 → 초안 재료 만들기
  → [새 단계] AI가 "잘못 적힌 말 → 맞는 표기" 쌍만 낸다
  → 코드가 쌍마다 검사하고, 통과한 것만 재료 글에 반영한다
  → 필드 고르기 → 줄 만들기
```

AI에게 글을 다시 쓰게 하지 않은 것은 이전 시험 때문이다. 요약 글을 AI가 다듬게 했더니 불확실 표시가 지워지고 내용이 빠졌다. 그래서 AI는 쌍만 내고, 글은 코드가 바꾼다.

바꿀 때는 원래 글을 남긴다.

```text
테로폰  →  테라폼(STT: 테로폰)
```

코드 검사는 세 가지로 시작했다.

| 검사 | 내용 |
|---|---|
| 출처 | 맞는 표기가 같은 요청 안에 글자 그대로 있어야 한다 |
| 소리 | 두 말을 자모로 풀어 비교한 비슷함이 기준 이상이어야 한다 |
| 숫자 | 숫자와 수를 나타내는 말은 바꾸지 않는다 |

소리 비교는 글자를 자음·모음으로 풀어 몇 개가 다른지 세는 방식이다. 테로폰과 테라폼은 0.71, 예산과 일정은 0.17이 나온다.

---

## 시도 1: 「」를 건드리지 않으면 고칠 것이 없었다

요약 글에는 「」로 묶인 부분이 있다. 요약을 만들 때 음성 인식 결과가 맞는지 확신할 수 없으면, 뜻을 짐작해서 고치지 않고 전사문을 그대로 옮긴 뒤 「」로 묶어 표시한다.

```text
「테로폰」 모듈은 다음 주에 정리하기로 함
```

처음에는 "「」로 묶인 글은 바꾸지 않는다"는 규칙을 넣으려 했다. 원문이니 건드리지 않는 것이 맞다고 생각했다.

구현 전에 실제 요약을 세어 봤다.

| 표기 | 위치 |
|---|---|
| 테로폰, 태로폰 | 「」 안 |
| 테라폼 | 「」 안 1번, 「」 밖 1번 |
| Terraform | 「」 밖 |

오인식은 모두 「」 안에 있었다. 이 규칙을 지키면 고칠 수 있는 것이 없다. 요약 쪽이 불확실하다고 표시한 곳이 바로 다시 봐야 할 곳이었다.

그래서 「」 안도 교정하기로 했다. 다만 「」 안의 글은 맞는 표기의 출처로는 쓰지 않았다. 확신하지 못한 글이 근거가 될 수는 없기 때문이다.

---

## 시도 2: 테라폼을 3번 모두 못 잡았다

첫 구현을 실제 회의 요약으로 3번 돌렸다. 「크레인」을 크레딧으로 고치는 것은 됐지만, 테라폼은 3번 모두 잡지 못했다.

원인은 이전에 넣은 다른 기능이었다. 초안에서는 요약 문장이 이미 담은 의견은 줄을 만들지 않는다. 「」 밖의 "테라폼"은 그렇게 빠진 의견에만 있었다. 재료에서 빠지니 출처에서도 빠졌다.

출처를 "재료 글"에서 "요청 안의 요약 글 전체"로 넓혔다. 줄이 되지 않은 의견도 요청에는 있는 글이다. 그 뒤로 테로폰, 태로폰 쌍이 나오기 시작했다.

---

## 시도 3: 글자 수가 같아야 한다는 규칙은 너무 좁았다

소리 검사에는 "글자 수가 같아야 한다"는 조건을 넣어 두었다. 뜻이 다른 말이 끼는 것을 막으려는 것이었다.

그런데 AI가 낸 "기능면 시선 → 기능 명세"가 이 조건에 걸렸다. 앞뒤 글을 보면 맞는 교정이었다. 음성 인식은 글자 수를 바꿔 적기도 한다.

조건을 빼면 무엇이 통과하는지 재 봤다. 담당자/담당(0.75), 회의록/회의(0.57)처럼 한쪽이 다른 쪽을 품는 쌍은 이미 다른 규칙이 막고 있었다. 남는 문제는 글자 수가 다른 쌍 중 소리가 어중간한 경우였다. 그래서 기준을 나눴다.

| 경우 | 비슷함 기준 |
|---|---|
| 글자 수가 같음 | 0.5 이상 |
| 글자 수가 다름 (2자 차이까지) | 0.6 이상 |

## 시도 4: 생각을 줄이면 빨라지지만 덜 잡는다

교정 호출 하나가 13~43초 걸렸다. 출력 토큰의 90% 이상이 모델이 답을 내기 전에 생각하는 토큰이었다. 생각하는 양을 `low`로 줄여 같은 입력으로 3번씩 쟀다.

| 설정 | 교정 호출 시간 | 검사를 통과한 쌍 (회차별) |
|---|---|---|
| 모델 기본값 | 29.9 / 23.9 / 20.5초 | 3 / 6 / 6개 |
| `low` | 12.0 / 12.3 / 14.3초 | 2 / 4 / 3개 |

시간은 절반이 됐지만 잡는 수도 줄었다. 초안 생성 기준이 5분 이내라서 시간에는 여유가 있다. 기본값을 골랐다.

## 시도 5: 영어 표기를 받자 "읽는 소리"가 새로 틀렸다

글자 수 규칙을 푼 뒤 AI가 "테로폰 → Terraform"을 내기 시작했다. 시험에 쓴 안건 글이 "AWS·Terraform"처럼 영어로 적혀 있었기 때문이다. 하지만 소리 비교는 한글끼리만 된다. 그래서 처음에는 한글 쌍만 받았고, 이 쌍은 버려졌다.

영어를 받으려면 비교할 소리가 필요하다. AI에게 읽는 소리를 함께 내게 했다.

```json
{"wrong": "태로폰", "right": "Terraform", "reading": "테라폼"}
```

코드는 "태로폰"과 "테라폼"을 비교한다. 읽는 소리가 잘못 적힌 말과 똑같으면 오인식이 아니라 표기만 바꾸는 것으로 보고 버린다. "에이더블유에스 → AWS" 같은 경우다.

합성 사례에서 교정이 10판 중 5판만 모두 맞았다. 놓친 것의 대부분은 ArgoCD였다. AI가 읽는 소리에 잘못 적힌 말 "알고 시디"를 그대로 넣어서, 방금 만든 규칙에 걸렸다. 지시문에 "reading은 바르게 읽은 소리다"라는 문장과 예시를 더했다.

## 시도 6: 전사 원문은 생각보다 도움이 안 됐다

맞는 표기가 요청에 없으면 회의 전사 원문에서 찾으려 했다. API 명세까지 먼저 정해 두었다. 구현 전에 같은 회의로 효과를 재 봤다. AI는 부르지 않고 코드로만 셌다.

| 항목 | 값 |
|---|---|
| 전사 줄 | 156줄 |
| 확신 낮은 줄을 뺀 줄 | 125줄 |
| 새로 생기는 맞는 표기 | 1개 ("기능 명세서") |
| 교정 입력 | 5,409자 → 약 10,680자 |

얻는 것이 1개인데 입력은 2배가 된다. 이유는 생각해 보면 단순했다. 요약의 「」 인용은 전사 원문에서 옮긴 글이다. 전사에도 같은 오인식이 들어 있다.

코드로 후보만 골라 보내는 방법도 재 봤다. 「」 안 낱말과 소리가 비슷한 전사 낱말을 고르니 후보가 335개 나왔다. 대부분 "정도/정보", "하면/가면" 같은 흔한 말이었다.

줄 단위 확신도의 한계도 보였다. 맞게 적힌 "기능 명세서"도 줄 전체는 확신 높음이지만, 글자별로는 0.21까지 내려갔다.

전사 원문은 명세만 남기고 지금은 쓰지 않기로 했다.

---

## 시도 7: 막은 것이 틀린 것은 아니었다

여기까지 와도 고쳐지지 않은 「」 인용이 47개 남았다. 하나씩 분류해 봤다. 정답이 없는 내 판단이라 개수는 대략이다.

| 분류 | 개수 |
|---|---|
| 맞는 글인데 인용한 것 | 약 27개 |
| 오인식이고 맞는 표기가 요청 안에 있음 | 약 4개 |
| 오인식인데 맞는 표기가 요청 어디에도 없음 | 약 10개 |
| 무슨 말인지 모름 | 약 6개 |

세 번째 줄이 문제였다. "어그 수정"(버그 수정), "요고사항 문서"(요구사항 문서)는 사람이 보면 바로 안다. 하지만 출처 검사가 막는다.

출처 검사를 빼면 위험하다는 근거로, 코드가 막은 쌍을 "엉뚱한 쌍"이라고 묶은 목록을 봤다. 그런데 하나씩 다시 보니 틀린 정리였다.

| 코드가 막은 쌍 | 막은 검사 | 다시 보니 |
|---|---|---|
| 젠킨수 → Jenkins | 출처 | 맞음 (합성 사례에 일부러 넣은 오인식) |
| 핼름 → 헬름 | 출처 | 맞음 (합성 사례에 일부러 넣은 오인식) |
| 클린 → 크레딧 | 소리 | 맞을 가능성이 높음 |
| 삼권 → (어느 학교 이름) | 소리 | 틀렸을 가능성이 높음 |
| 심화 → 기본 | 소리 | 틀렸을 가능성이 높음 |

"코드가 막았다"를 "AI가 틀렸다"로 읽고 있었다. 출처 검사가 막은 쌍 가운데 틀린 것은 이 목록에 없었다. 틀린 짐작을 막은 것은 소리 검사였다.

그렇다고 AI의 "앞뒤 글로 확실하다"는 판단을 믿을 수 있는 것은 아니다. 코드는 그 판단이 맞는지 확인할 수 없다. 소리는 비슷한데 틀린 짐작은 막지 못한다.

결정을 바꾼 것은 표시 방식이었다. 교정한 곳에는 원래 글이 늘 남는다.

```text
버그 수정(STT: 어그 수정)
```

짐작이 틀려도 회의록을 보는 사람이 원래 글을 보고 판단할 수 있다. 그래서 출처 검사는 없애고, 소리와 숫자 검사는 남겼다. 요청 안의 표기가 있으면 그것을 먼저 쓰고, 없으면 앞뒤 글로 분명할 때만 내게 지시문을 고쳤다. 출처 없이 받은 수는 로그에 따로 남긴다.

## 결과

실제 회의 요약으로 최종 설정의 초안을 2번 만들었다. 이 회의에는 정답이 없어서, 바뀐 곳이 맞는지는 앞뒤 글을 보고 판단했다.

| 바뀐 말 | 근거 | 2번 중 |
|---|---|---|
| 테로폰, 태로폰 → Terraform | 안건 글 | 2번 |
| 헬륨 셔츠, 헬름 상태도 → Helm 차트 | 안건 글 | 2번 |
| 비더블유에스 → AWS | 안건 글 | 2번 |
| 기능면 시선 → 기능 명세 | 안건 글 | 2번 |
| 크레디 → 크레딧 | 안건 글 | 2번 |
| 어그 수정 → 버그 수정 | 짐작 | 2번 |
| 요고사항 → 요구사항 | 짐작 | 2번 |
| 크레인 → 크레딧 | 안건 글 | 1번 |

단서가 없는 인용은 AI가 고치지 않았다. 소리가 먼 짐작 3쌍은 코드가 버렸다.

합성 사례(오인식 7개, 함정 포함) 10판의 결과다.

| 항목 | 결과 |
|---|---|
| 필드 고르기 맞음 | 10/10 |
| 교정이 모두 맞은 판 | 9/10 |
| 바뀌면 안 되는 말이 바뀐 경우 | 0건 |

처음 채점은 3/10이었다. "머지 리퀘스드"를 "Merge Request"로 고친 판을 채점이 틀림으로 셌기 때문이다. 맞는 표기를 여럿 받도록 고친 뒤 같은 결과를 다시 셌다.

시간은 늘었다.

| 단계 | 초안 전체 |
|---|---|
| 교정 없음 | 5.5초 |
| 출처가 있어야 고침 | 30.5 / 37.0초 |
| 최종 | 42.0 / 37.9초 |

초안 생성 기준인 5분 안이다. 요약 쪽도 오인식 교정을 작업하고 있어서, 그쪽이 충분히 잡게 되면 코드를 고치지 않고 끌 수 있도록 설정(`MINUTES_CORRECTION=0`)을 넣었다.

## 함께 돌아봐야 할 것

### 시험 조건이 실제보다 유리했을 수 있다

Terraform과 Helm 차트를 고친 근거는 안건 글이다. 그런데 이 시험의 안건 글은 회의를 듣고 직접 쓴 것이다. 실제 사용자가 회의 전에 쓴 안건에는 그 말이 없을 수 있다.

### 합성 사례 숫자는 단계끼리 그대로 비교할 수 없다

5/10에서 9/10이 됐지만, 그 사이에 사례와 채점 방식이 함께 바뀌었다. 지시문이 나아졌다는 근거로는 약하다.

### 회의 하나로 얻은 결론이다

전사 원문이 쓸모없다는 판단도, 비슷함 기준값도 이 회의 하나와 합성 사례에서 나왔다. #002에서 "회의 두 개로는 부족하다"고 적었는데, 이번에는 하나다.

### 남은 문제

| 문제 | 예 |
|---|---|
| 교정 뒤 조사가 맞지 않음 | 크레딧(STT: 크레디)와 |
| 수 낱말이 섞인 오인식을 버림 | 일 더블유에스 → AWS |
| 소리가 먼 교정을 버림 | 팬션 차트 → Helm 차트 (0.40) |
| 맞게 읽은 소리를 영어로 바꾸는 경우가 빠져나감 | 오가니제이션 → Organization |

## 정리

오인식을 고치는 단계를 넣으면서 처음에는 틀리게 고치는 것을 막는 데 집중했다. 「」는 건드리지 않고, 글자 수는 같아야 하고, 맞는 표기는 요청 안에 있어야 했다. 실제 회의로 돌릴 때마다 이 규칙들이 맞는 교정까지 막고 있다는 것이 드러났고, 하나씩 풀었다.

마지막 규칙을 풀 수 있었던 것은 AI를 믿게 되어서가 아니다. 틀려도 원래 글이 남아서 사람이 판단할 수 있기 때문이다.

> 검사가 막은 것은 위험한 것이지, 틀린 것이 아니다.

막힌 쌍을 틀린 쌍으로 읽으면 규칙이 맞다는 근거만 쌓인다. 무엇을 막았는지 하나씩 다시 보고 나서야 어느 검사를 남길지 정할 수 있었다.
