## 오늘의 개발 주제

[#003](/tripbranch/2026/07/23/tripbranch-devlog-003.html)에서 장소 상세 정보를 외부 API로 매번 조회하지 않고 DB에 미리 구축하기로 했다. 그 글의 다음 단계 7번은 "DB 조회 방식과 기존 API 방식의 응답 시간 비교"였다.

7월 31일, 조회 경로를 DB로 바꾸면서 이 비교를 했다. 장소 10곳의 상세 정보를 가져오는 시간이다.

| 경로 | 1회 | 2회 | 3회 | 평균 |
|---|---|---|---|---|
| 한국관광공사 API | 21.8초 | 20.1초 | 12.1초 | **18.0초** |
| DB | 0.82초 | 0.09초 | 0.07초 | **0.33초** |

"18.0초에서 0.33초로" 줄었다는 이 숫자는 발표 자료와 문서 여러 곳에 들어갔다.

발표 질의응답에서 "같은 조건에서 다시 재면 같은 결과가 나오느냐"는 질문을 받을 수 있다. 그래서 다시 쟀다. 결과는 재현되지 않았다.

이 글은 그 숫자를 어떻게 다시 확인했고, 결국 무엇으로 바꿔 말하기로 했는지 적은 기록이다.

---

## 다시 재 보니

같은 측정 스크립트로 날짜와 시간을 바꿔 여러 번 쟀다.

| 측정 시각 | 후보 수 | 관광공사 API | 장소당 | DB |
|---|---|---|---|---|
| 7/31 (금) 17시 | 10곳 | 18,001ms | **1,800ms** | 328ms |
| 8/8 (토) 03시 | 10곳 | 741ms | 74ms | 66ms |
| 8/9 (일) 12시 | 8곳 | 634ms | 79ms | 65ms |
| 8/10 | 8곳 | 718ms | 90ms | 57ms |

7월 31일 값은 발표에 쓴 평균이고 나머지는 중앙값이다. 7월 31일만 장소당 1,800ms이고, 나머지 세 번은 74~90ms였다. 20배 넘게 차이가 난다.

DB 쪽 첫 측정이 328ms로 높은 것은 1회차가 816ms였기 때문이다. 첫 연결을 맺는 시간이 들어가 평균을 끌어올렸다. 2회차부터는 매번 60~90ms 수준이었다.

### 시간대 때문인가

처음 떠올린 가설은 시간대였다. 7월 31일은 평일 퇴근 무렵이었고, 첫 재측정은 주말 새벽이었다. 외부 API가 붐비는 정도가 정반대인 조건이다.

그래서 낮 시간에 한 번 더 쟀다. 결과는 장소당 79ms로 새벽과 같았다. 시간대 가설은 맞지 않았다.

7월 31일에 왜 그렇게 느렸는지는 확인할 방법이 없다. 그날의 서버 상태나 네트워크 기록을 남기지 않았다.

### 18초도 실제로 일어날 수 있다

그렇다고 18초가 측정 실수였다고 볼 수도 없다. 그날 측정 안에서도 1회차 21.8초와 3회차 12.1초가 9.7초나 차이 났다. 재측정 중에도 한 번은 10초 시간 제한에 걸려 실패했고, 바로 다시 돌리자 741ms가 나왔다.

외부 API는 평소에는 빠르지만, 가끔 크게 늦어진다. 18초는 평소 값이 아니라 그 "가끔"이 찍힌 표본이었다.

## 그래서 무엇으로 말할 것인가

18초를 전형적인 값으로 내세우면 다시 재 보자는 요구에 답할 수 없다. 대신 측정 시점에 따라 흔들리지 않는 숫자를 찾았다.

> 추천 1회에 관광공사 API 호출 20회 → 0회

장소 10곳에 각각 상세 API를 2번씩 부르던 것이 DB 조회 1번으로 바뀌었다. 이 숫자는 언제 재도 같고, 코드를 보면 확인할 수 있다.

호출 수가 중요한 이유도 재측정 중에 직접 겪었다. 측정을 여러 번 돌리다가 관광공사 API의 **일일 호출 한도를 넘겼다.** 이후 요청은 전부 거부됐다. 추천 한 번에 20회를 부르는 구조라면, 사용자가 조금만 늘어도 하루가 끝나기 전에 서비스가 멈춘다.

이때 서비스가 가짜 데이터로 바꿔 대답하지 않고, "운영 정보를 가져오지 못했다"고 그대로 드러낸 것도 확인했다. 이 프로젝트에는 외부 API가 실패하면 가짜 데이터로 자동 전환하지 않는다는 원칙이 있다. 그 원칙이 실제 장애 상황에서 의도대로 동작한 첫 사례였다.

지금은 설정으로도 막아 두었다. 관광공사 API를 상세 조회 경로로 쓰면서 후보를 10곳보다 많이 잡으면 서버가 시작되지 않는다.

## 다시 재면서 알게 된 것

### 두 번 부르던 API 중 하나는 추천에 쓰이지 않았다

#003에서 "장소 상세 정보가 성격에 따라 두 개의 상세 API로 나뉘어 있다"고 썼다. 기본 정보 API와 소개·운영 정보 API다. 장소당 두 번씩 부르는 이유도 그것이었다.

응답을 정리하다가, 추천 점수 계산에는 운영 정보 API의 값만 쓰인다는 것을 확인했다. 점수 계산이 읽는 값은 운영시간과 휴무일뿐이고, 이름은 다른 곳에서 가져온다. DB 경로는 기본 정보 필드를 비워 둔 채로 이미 정상 동작하고 있었다.

추천만 보면 장소당 호출은 1번이면 충분했다. 기본 정보는 상세 함수가 한 번에 다 가져오도록 짜여 있어 딸려 온 것이다. 다만 "이곳 전화번호 알려줘" 같은 정보 질문에는 기본 정보가 필요하다.

### 사용자가 기다리는 시간은 다른 곳에서 생긴다

상세 조회가 요청 전체에서 얼마나 차지하는지도 쟀다. "경복궁 근처 카페 추천해줘"를 보냈을 때다.

| 단계 | 소요 시간 |
|---|---|
| 인공지능이 질문 해석 | 5.9~7.5초 |
| 장소·날씨·공휴일 조회 | 0.8~1.0초 |
| 인공지능이 답변 문장 작성 | 2.2초 |
| 합계 | 9.0~10.6초 |

인공지능 호출이 세 번이고, 합하면 전체의 90%다.

장소 조회를 DB로 바꾸면 조회 단계 안에서 0.73초가 0.20초가 된다. 그런데 이 단계는 장소·날씨·공휴일을 동시에 조회한다. 장소 조회가 빨라지면 0.55초 걸리는 공휴일 조회가 가장 늦게 끝나는 작업이 된다. 실제로 줄어드는 시간은 약 0.3초, 전체의 3%다.

사용자가 체감하는 응답 속도는 상세 조회로 정해지지 않는다. 이 전환의 실제 효과는 속도보다 호출 수와 한도 쪽에 있었다.

### 화면 로딩 표시는 측정값으로 정했다

9월에는 상세 모달을 열 때 서버에 보내는 요청을 따로 쟀다. 장소 정보 화면은 여전히 관광공사 API를 한 번 부른다. 24건을 쟀다.

| 최소 | 중앙값 | 90% 지점 | 최대 |
|---|---|---|---|
| 0.66초 | 0.73초 | 1.44초 | 1.63초 |

24건 모두 0.5초를 넘었고, 0.2초 안에 끝난 요청은 하나도 없었다.

이 값으로 로딩 표시 방식을 정했다. 로딩 화면을 0.2초 뒤에 띄우고, 최소 표시 시간은 두지 않는다. 0.2초 안에 끝나는 요청이 없으니 "떴다가 바로 사라져 화면이 깜빡이는" 경우가 생기지 않는다. 나중에 캐시를 붙여 빨라지면 그때 최소 표시 시간이 필요해진다.

## 함께 고려해야 할 문제

### 측정 결과 파일을 덮어쓰는 스크립트

측정 스크립트는 실행할 때마다 같은 결과 파일을 덮어쓴다. 18초의 원래 값도 저장소의 결과 파일에서는 이미 지워졌고, git 이력에만 남아 있었다. 측정 결과는 날짜를 붙여 새 파일로 남기는 쪽이 맞다.

### 진짜 병목은 아직 그대로다

요청 시간의 90%를 차지하는 인공지능 호출은 이번 작업에서 손대지 않았다. 질문 해석용 인공지능 호출을 두 번, 순서대로 하는 구조라, 줄이려면 그 구조부터 다시 봐야 한다.

## 정리

#003에서 세운 정적 DB 구조로 바꾼 뒤, 상세 조회가 18.0초에서 0.33초로 줄었다고 기록했다. 날짜와 시간을 바꿔 세 번 다시 재 보니 관광공사 API도 장소당 74~90ms였다. 18초는 가끔 생기는 지연이 그날 찍힌 표본이었다.

그래서 18초 수치는 더 쓰지 않고, 시간 대신 호출 수로 말하기로 했다. 추천 1회에 관광공사 API 20회가 0회가 됐다. 이 숫자는 언제 재도 같고, 일일 한도라는 실제 문제와 바로 이어진다.

다시 재는 과정에서, 요청 시간의 90%는 상세 조회가 아니라 인공지능 호출에서 생긴다는 것도 확인했다.

> 한 번 잰 숫자는 결과가 아니라 표본 하나다.

처음 측정 때 날짜만 바꿔 한 번 더 쟀다면, 18초를 대표값으로 쓰기 전에 편차부터 보였을 것이다.
