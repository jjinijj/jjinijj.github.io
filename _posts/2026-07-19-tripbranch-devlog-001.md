## 피드백을 받은 배경

TripBranch의 기능 범위와 추천 구조를 구체화하는 과정에서 강사님 피드백을 받았다.

이번 피드백의 목적은 개별 기능의 구현 방법을 확정하는 것이 아니라, 다음 내용을 점검하는 것이었다.

* 현재 기능 범위가 15일 MVP로 현실적인지
* 외부 API 기반 추천을 어떻게 개인화할지
* 혼잡도와 리뷰 데이터를 어디까지 활용할지
* 추천 및 프롬프트 성능을 어떻게 평가할지
* 데이터 수집과 구현을 어떤 순서로 진행할지

과제에서 요구하는 기능은 유지해야 하므로, TripBranch 자체 기능과 데이터 범위를 어떻게 축소할지가 핵심 논점이 되었다.

---

## 주요 질의응답

### 1. 15일 MVP 기능 범위

**질문**

과제 필수 기능과 TripBranch의 추천 기능을 모두 포함해 15일 안에 구현할 수 있는지 질문했다.

**피드백**

* 현재 계획한 기능은 15일 MVP로 구현하기에는 너무 많다.
* 서울 전체나 전국보다 혼잡도 데이터를 안정적으로 제공할 수 있는 특정 지역 또는 핫플로 범위를 제한하는 것이 좋다.
* 초기에는 핵심 기능을 단순하게 구현하고, 이후 조건문과 규칙을 추가하는 방식으로 확장하는 것이 적절하다.

> 과제 필수 기능은 유지하되, 서비스에서 다루는 지역·장소·데이터 범위를 축소해야 한다.

---

### 2. 단순 API 조회와 개인화 추천

**질문**

외부 장소 API에서 조회한 결과를 이용해 개인화 추천을 구현할 수 있는지 질문했다.

**피드백**

* API의 상위 검색 결과를 그대로 제공하면 일반 장소 검색과 차별성이 부족할 수 있다.
* 사용자가 여러 조건을 입력한 경우와 아무 조건도 입력하지 않은 경우를 나누어 설계해야 한다.
* API는 추천 후보를 가져오는 용도로 사용하고, 최종 순위에는 TripBranch의 자체 추천 기준을 적용해야 한다.

> API 조회 결과를 그대로 출력하는 것이 아니라 사용자 조건과 내부 가중치를 반영해야 한다.

---

### 3. 가중치 기반 추천 구조

**질문**

필터 기반과 가중치 기반 중 어떤 추천 구조가 적절한지, 가중치 방식에 복잡한 에이전트 구조가 필요한지 질문했다.

**피드백**

* 필터 기반은 조건을 순차적으로 적용하는 방식이고, 가중치 기반은 여러 조건을 종합해 순위를 산정하는 방식이다.
* 가중치 계산을 사용한다고 해서 반드시 복잡한 AI 에이전트 구조가 필요한 것은 아니다.
* MVP에서는 필수 조건으로 후보를 제거하고, 남은 후보를 가중치 점수로 정렬하는 구조가 현실적이다.

> `후보 조회 → 필수 조건 필터링 → 가중치 점수 계산 → 추천 이유 생성` 흐름으로 단순화할 수 있다.

---

### 4. 혼잡도 데이터의 지역 범위

**질문**

서울 121개 지역의 실시간 혼잡도와 그 외 지역의 일 단위 혼잡도 데이터를 모두 MVP에 포함할 수 있는지 질문했다.

**피드백**

* 혼잡도 데이터를 안정적으로 제공할 수 있는 지역만 대상으로 먼저 구현하는 방식을 권장받았다.
* 서울 전체도 범위가 넓을 수 있으므로 특정 핫플이나 제한된 지역으로 시작하는 것이 적절하다.
* 지역 범위를 줄이면 장소 매칭과 데이터 수집, 추천 검증에 필요한 작업량도 줄일 수 있다.

> 실시간 혼잡도를 핵심 가치로 보여주려면 혼잡도 데이터가 안정적인 지역으로 MVP를 제한하는 편이 유리하다.

---

### 5. 혼잡도 데이터의 최신성과 누락 처리

**질문**

실시간 혼잡도와 하루 단위 데이터를 동일한 가중치로 평가해도 되는지, 데이터가 없는 경우 나머지 가중치를 재계산해야 하는지 질문했다.

**피드백**

* 데이터 최신성과 누락 데이터를 처리하는 방법에는 정해진 답이 없다.
* 서비스 목적에 맞춰 팀 내부에서 기준을 정하고 직접 테스트해야 한다.
* 데이터가 없는 장소에 0점을 부여하면 실제 혼잡도가 아니라 데이터 제공 여부 때문에 불리해질 수 있다.

> 혼잡도 처리 방식은 기술적으로 정해진 답을 찾는 문제가 아니라 TripBranch의 추천 정책을 정의하는 문제다.

---

### 6. 외부 API와 데이터 확보 위험

**질문**

장소·날씨·운영·혼잡 정보를 외부 API나 크롤링으로 확보할 때 어떤 위험을 먼저 확인해야 하는지 질문했다.

**피드백**

* 외부로 전달되는 정보에 개인정보나 민감정보가 포함되는지 확인해야 한다.
* API 호출 제한과 데이터 누락에 대비한 예외 처리가 필요하다.
* 반복적인 크롤링은 차단될 수 있으므로 기존 공개 데이터나 정제된 데이터셋을 먼저 찾아보는 것이 좋다.

> 데이터가 존재하는지뿐 아니라 안정적이고 적절한 방식으로 수집·저장·사용할 수 있는지 확인해야 한다.

---

### 7. 장소와 리뷰 데이터 수집 순서

**질문**

장소 데이터와 리뷰 데이터 중 무엇을 먼저 수집해야 하는지 질문했다.

**피드백**

* 리뷰보다 추천 대상이 되는 장소 데이터를 먼저 확보해야 한다.
* 장소 목록을 정리한 뒤 해당 장소의 리뷰를 수집하고 전처리하는 순서가 적절하다.
* 장소가 확정되지 않은 상태에서 리뷰부터 수집하면 불필요하거나 중복된 데이터가 쌓일 수 있다.

> `지역·장소 범위 확정 → 장소 데이터 구축 → 리뷰 수집 → 리뷰 전처리·임베딩` 순서로 진행한다.

---

### 8. 리뷰 데이터 수집 범위

**질문**

서울 전체의 장소와 리뷰를 수집하는 것이 15일 MVP에 적절한지 질문했다.

**피드백**

* 서울 전체도 데이터 수집 범위가 넓을 수 있다.
* 크롤링과 전처리 시간을 줄이기 위해 특정 핫플이나 제한된 장소를 중심으로 진행하는 것이 좋다.
* 작은 범위에서 추천과 검색 품질을 먼저 검증한 뒤 확장하는 방식을 권장받았다.

> 데이터 수집 자체에 일정이 집중되지 않도록 대상 지역과 장소 수를 제한해야 한다.

---

### 9. 리뷰 임베딩과 장소 정보 연결

**질문**

리뷰에 장소명이 직접 언급되지 않은 경우 장소명과 리뷰를 합쳐 임베딩해야 하는지 질문했다.

**피드백**

* 장소 정보는 벡터 데이터베이스의 라벨 또는 메타데이터로 관리할 수 있다.
* 리뷰 본문을 임베딩하고 장소 ID, 장소명, 카테고리, 지역 등은 별도 메타데이터로 연결하면 된다.
* 장소명을 임베딩 문장에 포함하는 방식은 별도의 성능 비교 실험으로 확인할 수 있다.

> 리뷰 벡터와 장소 정보를 분리하고, 메타데이터를 통해 장소와 리뷰를 연결하는 방식이 적절하다.

---

### 10. 장소별 리뷰 개수 차이

**질문**

장소마다 리뷰 수가 다르면 리뷰가 많은 장소가 벡터 검색 결과에서 더 유리해지는지 질문했다.

**피드백**

* 검색된 리뷰의 절대 개수만 보지 않고 전체 리뷰 중 검색된 리뷰의 비율로 판단할 수 있다.
* 리뷰 수를 동일하게 맞추기보다 검색 개수, 검색 비율, 평균 유사도 등을 비교하는 것이 적절하다.
* 계산 방식별 테스트 결과를 기록해 추천 점수 설계의 근거로 활용해야 한다.

> 리뷰가 많은 장소가 자동으로 높은 점수를 받지 않도록 리뷰 수 차이를 보정해야 한다.

---

### 11. 리뷰 임베딩과 키워드 방식

**질문**

리뷰를 분석할 때 키워드 개수와 리뷰 임베딩 중 어떤 방식을 사용하는 것이 적절한지 질문했다.

**피드백**

* 단순 키워드 개수는 부정적인 문장에 포함된 단어까지 긍정 신호로 계산할 위험이 있다.
* 리뷰 전체 문맥을 반영하려면 문장 또는 리뷰 단위 임베딩 방식이 더 적절할 수 있다.
* 리뷰별 임베딩과 장소별 요약 임베딩 중 어떤 방식이 적합한지는 별도 실험이 필요하다.

> MVP에서는 리뷰 문맥을 반영할 수 있는 임베딩을 검토하되, 데이터 양과 검색 비용을 고려해 범위를 제한한다.

---

### 12. 프롬프트 A/B 테스트와 추천 평가

**질문**

인텐트 분류, 조건 추출, 사용자 조건 반영, 다중 턴 일관성, 추천 적합성 등을 평가 지표로 사용할 수 있는지 질문했다.

**피드백**

* 테스트용 데이터셋을 미리 제작한 뒤 동일한 데이터로 기능과 프롬프트를 검증해야 한다.
* 그때그때 다른 질문으로 평가하면 프롬프트 간 성능을 객관적으로 비교하기 어렵다.
* 단일 턴뿐 아니라 조건 누락, 조건 변경, 장소 거절 후 재추천 등의 다중 턴 시나리오도 필요하다.

> 같은 평가 데이터셋과 기준으로 프롬프트 A와 B를 비교하고 결과와 개선 과정을 기록해야 한다.

## 피드백에서 확인한 가장 큰 문제

### 1. 15일에 비해 기능과 데이터 범위가 너무 크다

과제 필수 기능만으로도 다음 항목을 구현해야 한다.

* 5개 인텐트별 프롬프트 설계
* CoT 적용 비교 실험
* 다중 턴 대화
* 대화 기억
* 실시간 데모 인터페이스
* A/B 테스트 환경

여기에 TripBranch의 추천 기능과 외부 데이터 조회, 리뷰 수집 및 임베딩까지 모두 포함하면 데이터 수집과 예외 처리에 일정이 집중될 위험이 크다.

기능을 단순히 제거하기보다 **서비스가 다루는 지역, 장소, 데이터 수를 줄이는 방식**으로 범위를 조정해야 한다.

### 2. 개인화 추천의 기준이 아직 구체적이지 않다

외부 API의 상위 장소를 그대로 보여주면 일반 장소 검색과 차별성이 부족하다.

특히 사용자가 별도의 조건을 입력하지 않은 경우 무엇을 기준으로 추천할지, 혼잡도와 리뷰를 최종 점수에 어떻게 반영할지가 정해지지 않았다.

따라서 API 검색과 TripBranch 추천을 구분할 수 있는 내부 추천 정책이 필요하다.

### 3. 완료 여부를 판단할 기준이 부족하다

현재는 기능 목록이 중심이며 다음과 같은 정량적 범위가 확정되지 않았다.

* 지원할 지역 수
* 추천 대상 장소 수
* 장소당 리뷰 수
* 평가 데이터셋 규모
* 기능별 통과 기준

이 기준이 없으면 15일 안에 구현할 수 있는지와 MVP가 완성되었는지를 판단하기 어렵다.

## 앞으로 가야 할 방향

### 1. 특정 지역과 제한된 장소로 범위 축소

혼잡도 데이터를 안정적으로 제공할 수 있는 특정 핫플 또는 일부 지역만 MVP 대상으로 선정한다.

장소 카테고리와 장소 수를 제한하고, 선택한 범위 안에서 추천 흐름을 완성하는 것을 우선한다.

### 2. 기본 추천 흐름 우선 구현

TripBranch의 MVP 흐름을 다음과 같이 단순화한다.

```text
자연어 요청
→ 인텐트 및 조건 추출
→ 누락된 필수 정보 재질문
→ 외부 API로 후보 장소 조회
→ 필수 조건 필터링
→ 가중치 기반 추천 점수 계산
→ 최대 3개 장소와 추천 이유 제공
→ 조건 변경 및 거절을 반영한 재추천
```

리뷰 임베딩과 정교한 개인화는 기본 추천 흐름이 완성된 이후 단계적으로 적용한다.

### 3. API, 추천 로직, LLM의 역할 분리

각 구성 요소의 책임을 다음과 같이 구분한다.

| 구성 요소  | 역할                            |
| ------ | ----------------------------- |
| 외부 API | 장소·날씨·운영·혼잡 후보 데이터 제공         |
| 추천 로직  | 필수 조건 필터링과 가중치 점수 계산          |
| LLM    | 자연어 입력 구조화, 재질문, 추천 이유 생성     |
| 대화 상태  | 이전 조건, 추천 장소, 거절 장소, 변경 조건 관리 |
| 벡터 DB  | 리뷰 벡터와 장소 메타데이터 저장 및 검색       |

추천 순위 결정은 LLM에 맡기지 않고 명시적인 규칙과 가중치로 처리한다.

### 4. 평가 데이터셋 우선 설계

5개 인텐트별 질문과 대표적인 다중 턴 시나리오를 사전에 작성한다.

평가 데이터셋에는 다음 상황을 포함한다.

* 정상적인 조건 입력
* 필수 조건 누락
* 기존 조건 변경
* 추천 장소 거절
* 이전 조건을 유지한 재추천
* API 오류
* 데이터 부족
* 추천 가능한 장소 없음

같은 데이터셋으로 프롬프트 A/B, 조건 추출, 대화 기억, 추천 결과를 반복 검증한다.

### 5. 정답이 없는 결정은 실험으로 검증

혼잡도 누락 처리, 가중치 비율, 리뷰 수 정규화, 임베딩 단위에는 정해진 하나의 답이 없다.

여러 방식을 비교하고 다음 내용을 기록한다.

* 어떤 방식을 비교했는지
* 어떤 평가 기준을 사용했는지
* 결과에 어떤 차이가 있었는지
* 최종 방식을 선택한 이유가 무엇인지

최종 결과뿐 아니라 의사결정 과정도 프로젝트의 중요한 산출물로 남긴다.

## 정리

이번 피드백을 통해 TripBranch의 가장 큰 문제는 기능 아이디어가 부족한 것이 아니라, **15일 안에 검증하기에는 기능과 데이터 범위가 너무 넓다는 점**임을 확인했다.

과제 필수 기능은 유지하되, 혼잡도 데이터를 안정적으로 사용할 수 있는 특정 지역과 제한된 장소를 대상으로 기본 추천 흐름을 먼저 완성해야 한다.

외부 API는 후보를 수집하고, 내부 추천 로직은 필수 조건과 가중치를 바탕으로 순위를 계산하며, LLM은 자연어 처리와 설명 생성을 담당하도록 역할을 구분한다.

리뷰 임베딩과 세밀한 개인화는 처음부터 전체 범위에 적용하지 않고, 제한된 데이터에서 효과를 검증한 뒤 확장한다.

> TripBranch의 15일 MVP 목표는 많은 기능을 구현하는 것이 아니라, 제한된 범위에서 개인화된 재추천 흐름을 끝까지 동작시키고 평가 가능한 결과를 만드는 것이다.
