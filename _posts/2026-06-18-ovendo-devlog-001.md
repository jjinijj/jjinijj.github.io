## 오늘의 개발 주제

Ovendo 프로젝트의 초기 방향을 정리했다.

이번 개발 일지에서는 왜 단순한 LLM 답변 생성기가 아니라, **Rule 기반 베이킹 어시스턴트**를 만들기 시작했는지 기록한다.

---

## 시작 배경

최근 AI, Retrieval, Agent 구조에 관심이 생기면서 자연스럽게 이런 생각을 하게 되었다.

> AI 프로젝트를 만든다면 결국 LLM을 붙이고, 질문하면 답이 나오게 만드는 걸까?

처음에는 그렇게 생각했다.

하지만 베이킹 관련 자료를 정리하고, 쿠키 실패 사례를 구조화하면서 생각이 조금 바뀌었다.

베이킹 문제에 대한 좋은 답변은 단순히 자연스럽게 생성되는 것만으로는 부족하다.
특히 실패 원인을 설명해야 하는 상황에서는 **어떤 근거를 통해 그 답에 도달했는지**가 중요하다.

예를 들어 “쿠키가 왜 안 퍼졌을까?”라는 질문에는 여러 원인이 있을 수 있다.

* 반죽 온도
* 버터 상태
* 밀가루 비율
* 설탕 종류
* 오븐 온도
* 휴지 시간

이런 상황에서 답변이 그럴듯하게 보이는 것보다 중요한 것은,
해당 답변이 **어떤 Rule과 근거를 기반으로 만들어졌는지 설명 가능해야 한다**는 점이었다.

그렇게 Ovendo를 시작하게 되었다.

---

## Ovendo는 무엇인가

Ovendo는 실험적인 베이킹 어시스턴트 프로젝트이다.

목표는 단순히 답을 생성하는 것이 아니다.
현재는 베이킹 지식을 구조화하고, 질문에 맞는 Rule을 찾아 근거 기반 답변을 구성하는 흐름을 만드는 데 집중하고 있다.

현재 목표는 다음과 같다.

* 베이킹 지식 구조화하기
* 질문 의도 분류하기
* 관련 Rule 찾기
* Rule을 근거로 답변 구성하기

현재 방향은 다음 문장으로 정리할 수 있다.

> Rule First, LLM Optional

LLM은 나중에 붙일 수 있다.
하지만 지금은 Rule 없이 답변을 생성하지 않는 구조를 먼저 만들고 있다.

---

## 처음 던진 질문

초기 테스트 질문은 다음과 같았다.

```text
왜 내 쿠키가 안 퍼졌을까?
```

처음에는 단순히 아래와 같은 구조를 떠올렸다.

```text
질문
↓

LLM
↓

답변
```

하지만 이 방식은 답변이 어떻게 만들어졌는지 추적하기 어렵다.

그래서 현재는 질문을 바로 LLM에 넘기지 않고, 먼저 질문을 분류하고 관련 Rule을 찾은 뒤 답변을 구성하는 방식으로 바꾸었다.

---

## 초기 설계 방향

현재 Ovendo의 구조는 다음과 같다.

```text
질문
↓

Question Classifier
↓

Rule Search
↓

Answer Builder
↓

LLM (선택)
↓

답변
```

핵심은 역할 분리이다.

각 단계의 역할은 다음과 같다.

| 단계                  | 역할                       |
| ------------------- | ------------------------ |
| Question Classifier | 질문의 의도와 관련 Rule 후보를 분류한다 |
| Rule Search         | 질문과 연결되는 Rule을 찾는다       |
| Answer Builder      | Rule을 기반으로 답변 구조를 만든다    |
| LLM                 | 필요한 경우 자연어 답변 생성을 보조한다   |

질문 이해, 지식 선택, 답변 구성을 분리하면 이후 구조를 바꿔도 전체 시스템이 크게 흔들리지 않는다.

---

## 현재 구현된 구조

현재 Ovendo는 아래 흐름까지 구현되었다.

```text
Question
↓

classifyQuestion()
↓

findRule()
↓

buildAnswer()
↓

AnswerResult
```

아직 복잡한 검색이나 LLM 연결은 없다.
하지만 질문이 들어오고, 분류되고, Rule을 찾고, 구조화된 결과를 반환하는 기본 흐름은 동작한다.

---

## 구현 내용

### 1. classifyQuestion()

`classifyQuestion()`은 사용자의 질문을 분류한다.

예를 들어 다음 질문이 들어온다.

```text
쿠키가 안 퍼져요
```

현재 분류 결과는 다음과 같다.

```text
intent:
troubleshooting

ruleId:
cookie_spread
```

현재는 v1 단계이기 때문에 키워드 기반 규칙으로 분류한다.

---

### 2. findRule()

`findRule()`은 분류 결과에서 나온 `ruleId`를 기준으로 Rule JSON을 조회한다.

현재 단계에서는 검색 점수 계산이나 유사도 비교는 없다.

```text
ruleId
↓

Rule 조회
```

즉, 지금은 “검색”이라기보다 “정해진 Rule ID로 Rule을 가져오는 단계”에 가깝다.

---

### 3. buildAnswer()

`buildAnswer()`는 찾은 Rule을 기반으로 `AnswerResult`를 만든다.

예시 결과는 다음과 같다.

```json
{
  "intent": "troubleshooting",
  "matchedRuleIds": [
    "cookie_spread"
  ]
}
```

현재는 자연어 답변을 생성하지 않고, 구조화된 결과만 반환한다.

이 방식의 장점은 답변 생성 전에 어떤 Rule이 매칭되었는지 먼저 확인할 수 있다는 점이다.

---

## 테스트 결과

CLI 테스트 중 흥미로운 결과가 있었다.

아래 질문은 정상적으로 분류되었다.

```text
쿠키가 안 퍼져요
```

하지만 비슷한 의미의 아래 질문은 분류에 실패했다.

```text
쿠키가 왜 안퍼질까요
```

결과는 다음과 같았다.

```text
intent:
unknown
```

원인은 현재 구조가 키워드 기반 분류이기 때문이다.

사람이 보기에는 두 질문이 거의 같은 의미지만, 현재 로직에서는 표현이 조금만 달라져도 매칭되지 않는다.

---

## 발견한 문제

이번 구현을 통해 알게 된 점은 다음과 같다.

> Rule 자체보다, Rule을 어떻게 찾는지가 더 어려운 문제일 수 있다.

Rule을 잘 만들어도 사용자의 질문이 다양한 표현으로 들어오면 적절한 Rule을 찾지 못할 수 있다.

예를 들어 아래 질문들은 모두 비슷한 의미일 수 있다.

```text
쿠키가 안 퍼져요
쿠키가 왜 안퍼질까요
쿠키가 너무 동그랗게 구워져요
쿠키가 납작해지지 않아요
반죽이 퍼지지 않고 그대로예요
```

이 표현들을 같은 문제로 연결하려면 단순 키워드 매칭만으로는 부족하다.

그래서 다음 단계에서는 Rule Search를 개선해야 한다.

---

## 다음 개발 목표

앞으로의 개발 방향은 다음과 같다.

```text
CLI 검증
↓

Rule Search 개선
↓

Embedding
↓

Retrieval
↓

LLM 연결
```

당장 LLM을 붙이는 것보다 먼저 해야 할 일은 Rule을 더 잘 찾는 구조를 만드는 것이다.

다음 단계에서는 다음 내용을 다룰 예정이다.

* 다양한 질문 표현 수집
* Rule Search 방식 개선
* 키워드 기반 분류의 한계 정리
* Embedding 적용 가능성 검토
* CLI 테스트 케이스 추가

---

## 오늘의 정리

Ovendo의 첫 실행은 성공했다.

아직은 작은 구조지만, 아래 흐름이 실제로 동작하기 시작했다.

```text
질문
↓

분류
↓

규칙 조회
↓

답변 결과 생성
```

이번 단계에서 가장 중요하게 확인한 것은 “답을 생성하는 것”보다 “답을 만들기 위한 구조를 분리하는 것”이었다.

Ovendo의 목표는 단순히 답을 잘하는 시스템이 아니다.

**왜 그런 답이 나왔는지 설명 가능한 베이킹 어시스턴트**를 만드는 것이다.

다음 개발 일지에서는 CLI 테스트와 Rule Search 개선 과정을 조금 더 자세히 다뤄볼 예정이다.
