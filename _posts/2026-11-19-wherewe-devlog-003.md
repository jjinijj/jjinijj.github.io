## 오늘의 개발 주제

WhereWe에는 AI 호출이 세 갈래 있다. 회의 중에 안건·요약·결정을 정리하는 실시간 분석(호출 A), 참석자를 돕는 회의 도우미(호출 B), 회의가 끝나면 회의록 초안을 쓰는 회의록 작성(호출 C)이다. [#001](/wherewe/2026/11/14/wherewe-devlog-001.html)과 [#002](/wherewe/2026/11/15/wherewe-devlog-002.html)는 호출 A 이야기였다.

이번에는 회의 도우미 에이전트를 끝냈다. 작업 네 개에 걸친 일이다.

| 작업 | 한 것 |
|---|---|
| 개인 질문 | 참석자가 물으면 오늘 회의 발언을 근거로 답한다 |
| 지난 회의록 검색 | 오늘 회의에 없는 내용은 확정된 지난 회의록을 찾아 답한다 |
| 먼저 알려주기 | 묻기 전에 "지난번엔 이렇게 정했어요" 같은 안내 카드를 띄운다 |
| 용어와 팀 용어집 | 처음 나온 약어를 설명하고, 확인된 설명은 다음 회의에서 다시 쓴다 |

만들고 나서 보니 구조가 단순했다. **질문과 먼저 알려주기는 들어오는 길만 다르고, 들어온 뒤의 에이전트는 하나다.** 이 글은 그 구조와, 만들면서 숫자를 보고 바꾼 결정들을 정리한다.

## 전체 구조: 입구 두 개, 에이전트 하나

```text
 [개인 질문]                          [먼저 알려주기]
 참석자가 질문 입력                    발언이 5줄쯤 쌓임 (요약과 같은 주기)
       │                                    │
       │                              후보 감지 (AI 없음: 규칙·임베딩 검색·형태소 분석)
       │                                    │
       │                              후보 선택 (점수순 · 중복 제거 · 1분 간격 · 1개)
       │                                    │
       ▼                                    ▼
 컨텍스트 (지금까지 전부)              컨텍스트 (후보가 된 발언까지만)
       │                                    │  + 후보 정보 (갈래, 미리 찾은 조각·발언)
       └──────────────┬─────────────────────┘
                      ▼
        ┌──────────── 에이전트 루프 (공통) ────────────┐
        │ 1. 이름·연락처 가리기                         │
        │ 2. 도구 루프 (Luna)                           │
        │    ├ search_past_minutes → 지난 회의록 검색   │
        │    ├ general_explanation (질문만)             │
        │    └ answer → 끝 (마지막 차례는 answer 강제)  │
        │ 3. 가린 값 되돌리기                           │
        └──────────────┬───────────────────────────────┘
       ┌───────────────┴────────────────┐
       ▼                                ▼
 답 검증                            카드 검증
 (근거가 실제로 있는가)             (만들 가치가 있는가, 80자, 근거 종류)
       ▼                                ▼
 질문한 사람에게만                  참석자 모두에게 카드
```

두 입구는 설정값 몇 개와 마지막 검증만 다르다.

| | 개인 질문 | 먼저 알려주기 |
|---|---|---|
| 입력 | 참석자의 질문 | 후보 (어느 발언이 왜 걸렸는지) |
| 컨텍스트 범위 | 지금까지 전부 | 후보가 된 발언까지만 |
| 답 모양 | 답 | 답 + "만들지 말지" + 제목 |
| 일반 설명 도구 | 있음 | 없음 (카드는 회의 근거로만) |
| 최대 호출 | 3회 | 2회 |
| 실패하면 | 폴백 모델로 한 번 더 | 카드를 안 만든다 |

카드 만들기는 "근거가 있을 때만 답하는 질문 하나를 AI가 스스로 던지는 것"이다. 후보 감지와 선택은 그 질문을 **언제** 던질지 적은 비용으로 정하는 앞단이다.

두 길은 한 곳에서 만난다. 카드의 [더 물어보기]를 누르면 그 카드를 인용한 개인 질문이 된다. 라이브 시험에서 "이번에는 얼마 예상이래?"라고 묻자, 카드에 나온 발언을 근거로 답했다.

## 오늘 회의는 검색하지 않고 통째로 넣는다

RAG라고 하면 먼저 검색부터 떠올리기 쉽다. 그런데 오늘 회의 내용은 검색하지 않는다. 그 시점까지의 발언 전체를 컨텍스트에 넣는다.

설계할 때는 1시간 회의를 1~2만 토큰으로 어림했다. 이 글을 쓰며 실측으로 다시 재 보니 그보다 컸다. 평가 대본 m01(5.9분, 94줄)의 질문 입력 토큰은 회의 1분마다 약 800토큰씩 늘었고, 같은 밀도로 1시간이면 약 5만 토큰이다(지시문 포함, 추정). 대본은 실제 회의보다 말이 촘촘해서 실제로는 이보다 작을 수 있다. 이 정도면 통째로 넣을 수 있는 크기이고, 검색으로 골라 넣다가 필요한 발언을 놓치는 위험이 더 크다고 판단했다. 검색과 통째로 넣기를 직접 비교해 본 것은 아니다.

검색은 양이 많고 오늘 회의 밖에 있는 **지난 회의록**에만 쓴다. 회의록을 확정할 때 조각으로 나눠 임베딩해 두고, 에이전트가 필요하다고 판단할 때 도구로 찾는다.

| 근거 | 어디서 | 화면 라벨 |
|---|---|---|
| 오늘 발언 | 컨텍스트 (전부) | 회의에서는 |
| 지난 회의록 | 도구 `search_past_minutes` (pgvector) | 지난 회의록에서는 |
| 팀 용어집 | 컨텍스트 (나온 용어만) | 팀 용어집에서는 |
| 일반 지식 | 도구 `general_explanation` | 일반 설명 |
| 없음 | – | "회의에서 나오지 않았어요" |

에이전트가 쓴 근거는 서버가 다시 확인한다. 컨텍스트에 없던 발언 번호, 이번에 검색하지 않은 회의록 조각, 질문 시점 뒤의 발언은 지운다. 근거가 다 지워진 부분은 "회의에서 나오지 않았어요"로 바꾼다. 모델이 "근거 있음"이라고 말하는 것을 그대로 믿지 않으려는 장치다.

## 먼저 알려주기: AI 없이 먼저 거른다

알려줄 거리를 찾을 때마다 AI를 부르면 비싸고 느리다. 그래서 감지는 AI 없이 한다. 갈래는 셋이다.

| 갈래 | 무엇을 보나 | 어떻게 |
|---|---|---|
| 용어 | 이번 회의에 처음 나온 약어 | 형태소 분석 + 규칙 |
| 지난 회의 | 지난 회의록과 이어지는 발언 | 발언 임베딩 → 회의록 조각과 코사인 유사도 |
| 오늘 회의 | "아까", "그 방식", 앞서 정한 결정과 겹치는 발언 | 정규식, 품사 패턴, 결정과의 유사도·핵심어 |

임베딩은 로컬 모델(multilingual-e5-small-ko)로 백엔드 안에서 돈다. 발언을 밖으로 보내지 않고, 질의 하나에 약 16ms 걸렸다(M1 MacBook Pro에서 3번 잰 평균). 한 번 임베딩한 발언은 회의 동안 메모리에 둬서 다시 계산하지 않는다.

걸린 후보 중 하나만 고른다. 한 번 볼 때 1개, 회의 시각으로 1분에 1개, 같은 대상은 회의당 1번이다. 고르지 않은 후보도 사유와 함께 DB에 남긴다. 갈래별로 몇 개가 걸리고 몇 개가 버려졌는지 세려고 남기는 것이다.

### 처음 정한 기준으로는 맞는 줄도 걸리지 않았다

지난 회의 갈래의 기준은 설계 때 유사도 0.9(과거 표현이 있으면 0.75)로 잡았다. 개발용 평가 대본 세 개(m01, m03, m04)를 AI 없이 감지만 돌려 보니 후보가 1개뿐이었다. 시험용으로 남겨 둔 m02는 개발 중에는 쓰지 않는다.

| 대본 | 지난 회의록 유사도 최고값 |
|---|---|
| m01 (지난 회의록과 같은 팀) | 0.73 |
| m03 (다른 팀) | 0.59 |
| m04 (다른 팀) | 0.50 |

m01에서 유사도가 높은 줄 8개를 열어 보니 모두 맞는 회의록 조각을 가리키고 있었다. 이 대본들에서는 기준이 너무 높았다. 같은 팀의 맞는 줄(실제로 지난 회의록과 이어지는 발언)은 걸리고 다른 팀 최고값(0.59)은 걸리지 않게 0.65(표현 있으면 0.60)로 낮췄다. 간격이 0.06뿐이라 데모 회의에서 다시 볼 값이다.

## 용어 찾기: "점수"가 아무것도 거르지 않고 있었다

용어 갈래는 이렇게 돈다.

```text
발언: "브이피시랑 서브넷은 테라폼으로 옮겼고, 알디에스가 남았어요"
  │
  ① 낱말로 쪼개기 (형태소 분석기 Kiwi)
  │   → 명사와 영문만 남김
  │
  ② 빼는 것
  │   흔한 명사 (국립국어원 학습용 어휘 3,167개 + 직접 적은 54개)
  │   사람 이름 (뒤에 "님·씨"가 붙은 말), 한 글자, 이번 회의에서 이미 나온 말
  │
  ③ 약어인가?
  │   영문 대문자 2~5자 (API, OOM)
  │   알파벳 이름으로만 된 한글 (브이피시 → VPC, 알디에스 → RDS)
  │   → 음성 인식이 영어를 한글로 적어서, 실제로는 이 규칙이 주로 걸린다
  │
  ④ 팀 용어집 확인
      ├ 확정 용어, 나온 회의 3개 미만 → 용어집 설명으로 바로 카드 (AI 0회)
      ├ 확정 용어, 3개 이상 → 팀이 아는 말이라 안 띄움
      └ 없음 → 후보
```

설계에는 점수 방식으로 적혀 있었다. 영문 약어 +2점, 사전에 없는 외래어 +1점, 2점 이상이면 후보. 그대로 만든 뒤, 사전에 없는 말을 1점으로 할지 2점으로 할지 비교하고 있었다. 그런데 점수가 어디에 쓰이는지 설명하다가 이상한 점을 발견했다.

| 낱말 | 점수 | 결과 |
|---|---|---|
| 약어 | 늘 2 | 늘 통과 |
| 사전에 없는 명사 | 늘 1 | 늘 탈락 |
| 둘 다 받는 낱말 | 없음 | – |

신호가 두 개뿐이고 겹치지도 않아서, **"2점 이상"이라는 기준은 실제로 아무것도 거르지 않았다.** 하는 일은 "약어면 후보"라는 규칙 하나였다. 이름만 점수라서 읽는 사람이 오해하기 쉬운 구조였다. 그래서 점수를 없애고 규칙으로 바꿨다.

사전에 없는 명사를 후보로 올렸을 때도 확인해 봤다. 후보가 6개에서 33개로 늘었고, "테라폼", "쿠버네티스" 같은 진짜 용어와 함께 사람 이름("서해반"), 음성 인식 오류("키오스코", "어플라"), 흔한 말("빌드")이 섞였다. 이것들을 구분할 방법이 먼저 필요해서, 지금은 후보로 올리지 않고 줄마다 몇 개 나오는지만 기록한다.

### 팀 용어집: 회의가 쌓일수록 설명이 쌓인다

```text
회의 중   용어 카드가 나감 → 설명을 용어집 "대기"에 저장
회의 뒤   회의록 확정 때 진행자가 확인 → 체크하면 확정, 해제하면 제외
다음 회의 그 말이 나오면 용어집 설명으로 바로 카드 (AI 0회)
          세 회의 이상 나온 말은 팀이 아는 말로 보고 더 띄우지 않음
```

AI가 만든 설명을 사람이 한 번 보고 넣는다. 확인 없이 넣으면 틀린 설명이 회의마다 반복되기 때문이다. 회의 중 공용 보드의 "AI가 먼저 올리고, 사람은 틀린 것만 뺀다"는 원칙과 같다.

## 한 번 돌린 결과로는 알 수 없었다

용어집을 근거로 쓰도록 개인 질문 지시문을 v3.0에서 v4.0으로 올렸다. 지난 회의록 질문 8개로 비교했더니 v3.0은 7/8, v4.0은 5/8이었다. 지시문을 고쳐서 나빠진 것처럼 보였다.

그런데 질문마다 한 번씩만 돌린 결과였다. 같은 조건으로 두 번씩 더 돌렸다.

| 실행 | v3.0 | v4.0 |
|---|---|---|
| 처음 | 7/8 | 5/8 |
| 반복 1 | 7/8 | 7/8 |
| 반복 2 | 7/8 | 7/8 |

두 버전 모두 같은 질문 하나만 틀렸다. 처음의 5/8은 실행마다 생기는 흔들림으로 보인다. 한 번만 보고 v4.0을 버렸다면, 멀쩡한 지시문을 되돌리고 있었을 것이다.

카드는 흔들림이 더 컸다. 같은 카드 지시문을 두 모델로 두 번씩 돌렸다. 표의 상기 카드는 오늘 회의 갈래에서 나오는 카드로, 앞서 한 이야기를 다시 알려 준다. 평가 대본에서 내용상 만들어야 하는 상기 카드가 하나 있다.

| 실행 | 지난 회의 카드 | 만들어야 하는 상기 카드 | 용어 카드 |
|---|---|---|---|
| gpt-6-luna 1회 | 2/2 | 만들지 않음 | RDS, CPU |
| gpt-6-luna 2회 | 1/2 | 만듦 | RDS |
| gpt-5.6-luna 1회 | 2/2 | 만듦 | RDS |
| gpt-5.6-luna 2회 | 2/2 | 만듦 | HNSW, IAM, CPU |

만든 카드는 모두 근거와 내용이 맞았다. 다만 "만들지 말지"는 실행마다 달랐다. 5.6이 더 고르게 나왔지만 두 번씩이라 모델 차이로 단정하지 않았다.

이 과정에서 카드 지시문의 문제 두 가지도 드러났다.

- **용어 판단 기준이 없었다.** "참석자 누구나 아는 말이면 만들지 않는다"고만 적혀 있었다. 개발팀 회의에서 모델은 "이 팀은 LLM, RDS를 다 안다"고 보고 카드를 거의 안 만들었다. 기준을 "이 분야를 모르는 참석자"로 정했다. 팀이 아는 말을 거르는 일은 용어집의 "세 회의" 규칙이 맡는다.
- **지금 막 한 말을 "앞서 정했다"고 썼다.** 상기 카드가 지금 발언에서 처음 나온 내용을 "앞서 ~하기로 했어요"라고 쓰고, 근거는 그 내용이 없는 다른 줄로 달았다. 서버 검증은 "근거 줄이 지금보다 앞인가"만 봐서 통과했다. 그래서 지시문에 "지금 발언에서 처음 나온 내용은 상기 카드로 만들지 않는다"는 규칙을 넣었다.
- **후보 자체가 엉뚱했다.** 규칙을 넣은 뒤 반복 실행에서, 같은 후보가 이번에는 관련 없는 결정을 다시 알려 주는 카드를 만들었다. 열어 보니 "다음", "결과" 같은 흔한 말 두 개가 겹쳤다고 결정 겹침 후보로 잡혀 있었다. 용어 갈래에서 만든 흔한 명사 목록의 말은 겹친 말로 세지 않도록 고치자 그 후보가 사라졌다.

## 함께 돌아봐야 할 것

### 카드를 만들지 말지는 아직 흔들린다

같은 입력에 어떤 실행은 카드를 만들고 어떤 실행은 안 만든다. 데모에서 매번 같은 카드가 뜰 것이라고 기대하면 안 된다. 데모 회의로 다시 재고, 필요하면 모델을 바꿔 비교한다.

### 재지 못한 갈래가 있다

"아까", "그 방식"처럼 앞을 가리키는 말은 5분 넘게 앞의 발언을 가리킬 때만 후보로 잡는다. 평가 대본에는 그런 경우가 없어서 한 번도 걸리지 않았다. 규칙은 있지만 실측은 없다.

### 지난 회의록이 아직 가짜다

지난 회의록 검색과 지난 회의 카드는 동작한다. 그런데 지금 그 회의록은 직접 쓴 가상 회의록 두 개를 시드로 넣은 것이다. 오늘 회의가 끝나서 다음 회의의 "지난 회의"가 되는 고리는 회의록 작성과 확정이 생겨야 이어진다.

## 정리

회의 도우미는 결국 하나의 에이전트다. 묻는 사람이 참석자면 개인 질문이고, 묻는 쪽이 서버의 감지 규칙이면 먼저 알려주기다. 그래서 두 기능을 따로 만들지 않고, 감지와 선택이라는 앞단만 더했다.

숫자를 보고 바꾼 것도 많았다. 맞는 줄도 못 거는 기준을 낮췄고, 아무것도 거르지 않던 점수를 규칙으로 바꿨고, 흔한 말 두 개로 걸리던 후보를 걸렀다. 그리고 지시문이 나빠졌다고 결론 내기 직전에 한 번 더 돌려 봤다.

> 한 번 돌린 결과로는 지시문이 나빠진 건지 모델이 흔들린 건지 알 수 없다.

반복해서 재기 전까지는, 차이처럼 보이는 숫자를 차이라고 부르지 않기로 했다.
